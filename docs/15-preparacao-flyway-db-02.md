## 3. Modelo relacional proposto

Não há `@Table` nas entidades; os nomes explícitos não foram fixados por anotação. Com a estratégia física padrão do Spring Boot/Hibernate, os nomes esperados são `usuario`, `quadra` e `agendamento`, e os campos Java camelCase são convertidos para snake_case. Confirmar essa estratégia/nome físico em teste antes de aplicar migration.

```text
usuario (1) ───────< agendamento >─────── (1) quadra
                    usuario_id NOT NULL
                    quadra_id   NOT NULL
```

Proposta:

- `usuario`: identidade, nome, e-mail único, telefone, senha codificada e perfil.
- `quadra`: identidade, nome, tipo e estado ativo.
- `agendamento`: identidade, data, hora inicial/final, status, `criado_em`, FKs para usuário e quadra.
- FKs sem `ON DELETE CASCADE` (equivalente a `NO ACTION`/comportamento padrão): preserva a integridade e impede apagar usuário/quadra referenciados. Isso corresponde à relação JPA sem cascade e às verificações de exclusão dos serviços.
- `criado_em` será `TIMESTAMPTZ NOT NULL DEFAULT statement_timestamp()`. Para o atual banco de desenvolvimento vazio, a migration inicial pode criar o campo desde o início; não há timestamp histórico a backfill se a ausência de tabelas continuar confirmada.
- Status SQL deve aceitar somente `PENDENTE`, `CONFIRMADO`, `CANCELADO`, `EXPIRADO`; default proposto `PENDENTE` reforça a regra mesmo em INSERT que omita status.
- Constraint `CHECK (hora_fim > hora_inicio)` impede duração zero/negativa e atravessar meia-noite, inclusive fora da API.
- Constraint `EXCLUDE` parcial mantém sobreposição proibida apenas nos status bloqueadores.

## 4. Tipos SQL e restrições

| Tipo Java/JPA | SQL proposto | Evidência/observação |
|---|---|---|
| `Long` + IDENTITY | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `GenerationType.IDENTITY` nas três entidades. |
| `String` sem `length` | `VARCHAR(255)` | Tamanho não é explicitado em `@Column`; 255 é o default JPA/Hibernate esperado. |
| `LocalDate` | `DATE` | Sem timezone. |
| `LocalTime` | `TIME WITHOUT TIME ZONE` | Fim deve ser maior que início. |
| `boolean` | `BOOLEAN` | `ativa` não nulo. |
| Enum `EnumType.STRING` | `VARCHAR(255)` + `CHECK` opcional/recomendado | Persiste nomes, não ordinais. Incluir `EXPIRADO` após atualização do enum. |
| `Instant` (novo) | `TIMESTAMPTZ` | Geração pelo banco para evitar relógios divergentes entre instâncias. |

Validações dos DTOs não são tamanhos de coluna: `UsuarioRequestDTO.nome` tem 3–100 caracteres e senha mínimo 6 (`UsuarioRequestDTO.java:13–30`), mas as colunas não declaram `length`; e-mail/telefone também não têm limite JPA. A migration inicial deve espelhar o modelo JPA (255 para strings) ou coordenar qualquer tamanho mais restrito com alterações de entidade/validação em etapa posterior. Não inventar limites SQL incompatíveis.

### Chaves, unicidade e índices

- PKs em `id`; identidade gerada por PostgreSQL.
- `usuario.email` é único (`Usuario.java:29–30`), portanto migration cria constraint/índice UNIQUE.
- `agendamento.usuario_id` e `agendamento.quadra_id` são FKs não nulas (`Agendamento.java:35–41`), sem cascade configurado.
- Não há `@Index`, `@Table(indexes=...)` ou schema SQL atualmente. PostgreSQL não cria automaticamente índice B-tree para cada FK.
- A constraint GiST cria o índice de exclusão para `quadra_id` + range. Considerar índice `(quadra_id, data)` para pré-consultas e índice parcial `(criado_em) WHERE status='PENDENTE'` para a rotina de expiração; validar plano/carga antes de manter índices redundantes.
- `Usuario`/`Quadra` não têm `@Version`; controle otimista de edição não faz parte do schema DB-02.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE usuario (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    telefone VARCHAR(255) NOT NULL,
    senha VARCHAR(255) NOT NULL,
    perfil VARCHAR(255) NOT NULL,
    CONSTRAINT uq_usuario_email UNIQUE (email),
    CONSTRAINT ck_usuario_perfil CHECK (perfil IN ('ADMIN', 'CLIENTE'))
);

CREATE TABLE quadra (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(255) NOT NULL,
    tipo VARCHAR(255) NOT NULL,
    ativa BOOLEAN NOT NULL,
    CONSTRAINT ck_quadra_tipo CHECK (
        tipo IN ('FUTVOLEI', 'BEACH_TENNIS', 'VOLEI_AREIA')
    )
);

CREATE TABLE agendamento (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    data DATE NOT NULL,
    hora_inicio TIME WITHOUT TIME ZONE NOT NULL,
    hora_fim TIME WITHOUT TIME ZONE NOT NULL,
    status VARCHAR(255) NOT NULL DEFAULT 'PENDENTE',
    criado_em TIMESTAMPTZ NOT NULL DEFAULT statement_timestamp(),
    usuario_id BIGINT NOT NULL,
    quadra_id BIGINT NOT NULL,
    CONSTRAINT ck_agendamento_horario CHECK (hora_fim > hora_inicio),
    CONSTRAINT ck_agendamento_status CHECK (
        status IN ('PENDENTE', 'CONFIRMADO', 'CANCELADO', 'EXPIRADO')
    ),
    CONSTRAINT fk_agendamento_usuario FOREIGN KEY (usuario_id)
        REFERENCES usuario(id) ON DELETE NO ACTION ON UPDATE NO ACTION,
    CONSTRAINT fk_agendamento_quadra FOREIGN KEY (quadra_id)
        REFERENCES quadra(id) ON DELETE NO ACTION ON UPDATE NO ACTION,
    CONSTRAINT ex_agendamento_quadra_periodo_bloqueante
        EXCLUDE USING gist (
            quadra_id WITH =,
            (tsrange(data + hora_inicio, data + hora_fim, '[)')) WITH &&
        )
        WHERE (status IN ('PENDENTE', 'CONFIRMADO'))
);

CREATE INDEX ix_agendamento_usuario_id ON agendamento (usuario_id);
CREATE INDEX ix_agendamento_quadra_data ON agendamento (quadra_id, data);
CREATE INDEX ix_agendamento_pendente_criado_em
    ON agendamento (criado_em)
    WHERE status = 'PENDENTE';
```

### Observações sobre o SQL

- Os nomes SQL seguem a estratégia física padrão (`usuario`, `quadra`, `agendamento`, `hora_inicio`). Como as classes não fixam `@Table`/`@Column(name=...)` em todos os campos, confirmar no teste de schema antes da aplicação.
- `btree_gist` é exigido para `quadra_id WITH =` no GiST. O driver JDBC presente no projeto não instala a extensão; ela é criada pela migration e pode exigir privilégio do usuário de banco.
- A exclusion constraint aplica-se só a PENDENTE/CONFIRMADO. Mudar status para CANCELADO/EXPIRADO em transação libera a faixa ao commit.
- `CHECK hora_fim > hora_inicio` preserva a regra de não atravessar meia-noite fora do serviço.
- O JPA atual seta `PENDENTE` e `CLIENTE` nos serviços; migration propõe default de PENDENTE para novas linhas SQL que omitam status. Não há default de perfil ou `ativa` definido nas entidades.
- O índice UNIQUE de e-mail e PKs já criam seus próprios índices; não duplicá-los. Índices de FK e consulta devem ser medidos no PostgreSQL real.
- Os tamanhos padrão `VARCHAR(255)` espelham as anotações JPA sem `length`. Se forem aprovados tamanhos menores, alinhar DTO, entidade e migration.
- A semântica do CHECK de status pressupõe que `EXPIRADO` esteja no enum Java antes de a aplicação ler/escrever esse valor. Confirmar se a coluna real é VARCHAR; se for enum nativo ou existir CHECK antigo, criar ajuste compatível.
- Não há `criadoEm` atualmente; ele precisa ser mapeado como valor gerado pelo banco e recuperado após INSERT. Testar a estratégia Hibernate escolhida, não preencher com relógio JVM paralelo.

- O starter Boot inclui integração Flyway/JDBC e `flyway-core`; para PostgreSQL, a documentação Spring Boot 4.x exige o módulo de banco `org.flywaydb:flyway-database-postgresql`.

Esses artefatos não foram adicionados. O driver `org.postgresql:postgresql` já está presente e não precisa ser duplicado. A compatibilidade foi verificada contra o dependency BOM local 4.0.7 e os POMs publicados; não foi feito build/dependency resolution nesta etapa.

### Configuração Flyway sugerida

- Migrations em `classpath:db/migration`, com nomes versionados `V1__create_arena_schema.sql`, `V2__...sql`.
- Flyway deve ser a única autoridade de DDL; não combinar migrations com `schema.sql` nem deixar Hibernate alterar schema.
- `spring.jpa.hibernate.ddl-auto=validate` valida mappings após a migration; não cria/tenta atualizar tabelas.
- Flyway habilita por auto-configuração quando os módulos estão no classpath; declarar `spring.flyway.enabled=true` explicitamente é opcional/documental.
- Spring Boot executa migrations durante inicialização e coordena a criação do `EntityManagerFactory`; manter um único mecanismo de schema.

Referência oficial: [Spring Boot 4.x — Database Initialization / Flyway](https://docs.spring.io/spring-boot/4.0/how-to/data-initialization.html). Versões gerenciadas: [BOM Spring Boot 4.0.7](https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-dependencies/4.0.7/spring-boot-dependencies-4.0.7.pom).

## 8. Estratégia de validação do schema pelo Hibernate

Com Flyway gerindo DDL, a configuração recomendada é `spring.jpa.hibernate.ddl-auto=validate`. A ordem esperada é:

1. Spring Boot constrói datasource usando `SPRING_DATASOURCE_*`.
2. Flyway conecta ao database e executa migrations pendentes em `db/migration`, registrando `flyway_schema_history`.
3. Hibernate reconhece entidades sob `br.com.arena.model` via package raiz `br.com.arena` de `ArenaApplication`.
4. Hibernate valida tabelas/colunas e tipos mapeados; se divergir, a inicialização falha em vez de alterar schema. A validação não substitui testes explícitos de constraints, índices e da EXCLUDE criados pelo SQL.

As relações JPA do mapeamento esperado são:

- `Usuario` 1:N `Agendamento` (`mappedBy="usuario"`).
- `Quadra` 1:N `Agendamento` (`mappedBy="quadra"`).
- `Agendamento` N:1 obrigatório para cada um, com `usuario_id` e `quadra_id`.

`@OneToMany` não adiciona FKs ou cascade por si; as FKs residem em `agendamento`. Não usar `create`, `create-drop` ou `update` como configuração compartilhada/produtiva. O README mostra `update` apenas como instrução antiga, não como valor ativo.

## 9. Riscos e decisões antes de implementar

- **Nomes físicos:** confirmar estratégia Hibernate/Spring Boot 4 em teste e validar schema migration; tabelas não têm `@Table`, campos não têm nome explícito salvo `@JoinColumn`.
- **Tamanho de String:** anotações não fixam limites SQL; default JPA/Hibernate é 255. DTO tem regras diferentes (`Usuario.nome` máximo 100, senha mínimo 6), mas não reduzir coluna sem alinhar entidade/validação.
- **Defaults:** serviço define `Usuario.perfil=CLIENTE` e `Agendamento.status=PENDENTE`; `Quadra.ativa` é boolean primitivo e mapper persiste o valor recebido. Distinguir defaults de aplicação e defaults SQL da migration.
- **Exclusão e histórico:** FKs `NO ACTION` sem cascade preservam referências; serviços atuais recusam apagar usuários/quadras com agendamentos. Cancelamento futuro muda status, não apaga a relação.
- **Índices:** PKs e UNIQUE email geram índices; PostgreSQL não cria índice B-tree automaticamente em cada FK. A migration propõe índices para consulta de disponibilidade, usuário e vencimento; validar planos/cardinalidade.
- **Extensão/constraint:** confirmar `btree_gist` disponível e permissões no PostgreSQL 16 alvo. V1 não deve ser aplicada até validar o DDL e a condição parcial de status.
- **Conexão:** `POSTGRES_*` no Compose não fornece `SPRING_DATASOURCE_*` ao processo local; não deixar senha em Git/README.
- **Testes:** teste atual `contextLoads` historicamente falha sem URL datasource. A migration deve ser validada em schema vazio descartável antes de apontar o IntelliJ para dados persistentes.
- **DB-02:** nenhuma constraint, Flyway ou migration existe hoje; o código ainda não contém `EXPIRADO` nem `criadoEm`.
- **Outros componentes:** não habilitar `ddl-auto=update` em paralelo com Flyway. Testar também o arranque da API com segredo JWT configurado fora do repositório.

## 10. Sequência recomendada de implementação e testes

1. **Configuração local — OBRIGATÓRIA:** criar configuração de dev com datasource externo por env e `ddl-auto=validate`; manter senha/JWT fora do Git. Não abrir a aplicação a produção via `update`.
2. **Flyway — OBRIGATÓRIA:** adicionar `spring-boot-starter-flyway` e `flyway-database-postgresql`, criar `V1__create_arena_schema.sql` com tabelas/PKs/FKs/UNIQUE/CHECKs e a constraint GiST parcial aprovada.
3. **Timestamp/estado — OBRIGATÓRIA:** implementar `criadoEm` como coluna DB-generated e `EXPIRADO` no enum/DTO de resposta; migrations precedem código que lê/escreve o status novo.
4. **Integração JPA — OBRIGATÓRIA:** testar persistência de Usuario, Quadra, Agendamento, geração IDs, enums, FKs, default `PENDENTE`, timestamp retornado e Hibernate `validate`.
5. **DB-02 — OBRIGATÓRIA:** serviço transacional e prechecks para create/update; mapear apenas `23P01` para 409; preservar as validações DB-01 e autorização SEG-01.
6. **Estados — OBRIGATÓRIA:** PATCH cancellation, PATCH confirmação ADMIN, remoção do DELETE físico, guards de reagendamento e job `@Scheduled`; testar a corrida confirmação/expiração.
7. **Testes PostgreSQL — OBRIGATÓRIA:** executar migrations e testes concorrentes em Postgres 16 descartável (Testcontainers ou CI isolado), sem reusar o volume de desenvolvimento.
8. **Clientes guest — FUTURA:** numa etapa separada, projetar reserva sem `Usuario` autenticado, verificação OTP/WhatsApp e autorização/recovery; a constraint temporal continua independente do cliente.

Testes mínimos:

- `V1` parte do schema vazio e cria o modelo JPA esperado; `flyway_schema_history` registra a versão.
- Hibernate `validate` passa no schema migrado e falha numa divergência intencional de teste.
- INSERT PENDENTE, atualização de status, CHECK de hora, enums, FKs/NO ACTION e unicidade de email.
- Constraint permite adjacentes e rejeita intervalos iguais/parciais/contidos na mesma quadra.
- Cancelar/expirar conserva a linha e libera a faixa; confirmar conserva o bloqueio.
- Duas conexões concorrentes disputam intervalo; exatamente uma confirma e a outra recebe conflito 409.
- SEG-01/DB-01 permanecem cobertos, inclusive PUT sem `usuarioId`, operação ADMIN de reatribuição e atualização de quadra/horário.

## Conclusão

Flyway é compatível com o parent Spring Boot 4.0.7 e adequado para esta estrutura SQL PostgreSQL-específica. A combinação recomendada é Flyway como único gerador de schema e Hibernate `validate`. O schema SQL proposto deve seguir os mappings acima e adicionar `criado_em`, enum `EXPIRADO`, CHECK temporal e constraint parcial `EXCLUDE`; nenhuma dessas alterações foi aplicada.
